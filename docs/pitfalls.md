# 踩坑记录

按"踩到的顺序"排列。每条都包含现象、原因、解法——只写现象不写解法的坑没有参考价值。

---

## 1. `search-poi --category` 必须用中文值

**现象**：传英文类别值直接报错，且报错信息不提示"应该用中文"。

**原因**：`--category` 支持 36 类**中文枚举**（演出赛事、体育场馆、主题乐园、历史古迹等），不接受英文值。

**解法**：统一使用中文枚举值，并把可用类别清单写进系统提示词，让模型不需要试错。

**教训**：工具参数的取值域如果不在文档里，就必须写进提示词。否则模型会自己猜一个英文词然后失败。

## 2. 飞猪数据真实，但季节性强到会毁掉演示

**现象**：彩排时能查到的赛事，正式演示当天已经开完或售罄；同一个查询，换个周末结果完全不同。

**原因**：赛事 / 演出供给按周末排期波动，且数据实时变化。

**解法**：
1. **演示前实查当前周末供给**，不用彩排时的缓存结果
2. 把"无赛事"当成**正常路径**而非异常——智能体已有三套兜底话术
3. 演示时**主动展示兜底**，而不是回避它

**这条为什么反而是加分项**：一个只会在顺利路径上跑的系统，和一个能在真实供给缺失时如实告知并给出替代路径的系统，后者更可信。我们在演示中刻意保留了这个环节（第 2 幕、第 5 幕各触发一次），因为它证明了数据是真的——**编数据的人不会给自己安排"查不到"的剧情**。

---

## 3. 百炼智能体编辑页的版本冲突

**现象**：修改配置保存时报"版本冲突"，改动丢失。

**原因**：百炼智能体有版本机制。多标签页 / 多端并发编辑，或基于旧版本修改后保存，都会冲突。

**解法**：每次修改前先刷新到最新版本，基于最新版本保存；改动较大时**新建版本**而不是覆盖旧版本。

**副作用（好的）**：版本机制意外地帮我们留下了 v1→v6 的完整迭代记录，第 8 条就是从这个记录里整理出来的。

---

## 4. `FLYAI_API_KEY` 没注入会话时会静默降级

**现象**：以为一直在跑自己的额度，实际消耗的是公共试用额度，直到被限流才发现。

**原因**：百炼会话需要**在会话级环境变量里**填 Key，只配在智能体上不一定生效。未配置时 `flyai-cli` 会回落到内置的公共试用 Key，**不报错**。

**解法**：
1. 每次新建会话后，**先确认返回结果里没有"体验模式"字样**，再开始演示
2. 把这一步写进演示前检查清单

**教训**：静默降级比直接报错危险得多。所有"不报错但走错分支"的行为都要显式检查。

## 5. 飞猪返回的火车数据有方向性差异

**现象**：A→B 能查到直达车次，B→A 只返回换乘甚至查不到。

**原因**：铁路数据本身有方向性，不是接口 bug。

**解法**：
1. **去程和回程必须分方向各查一次**，不能复用同一次查询的结果
2. **如实标注，不硬说直达**——查到换乘就说换乘

**这条踩坑在演示里变成了亮点**：用户问"有没有 Z587 这种 Z 字头直达"，智能体查完返回 Z333（去程）和 Z588（回程），并**主动纠正"Z587 方向反了"**。这个纠错行为本身就是"数据来自真实查询"的证据。

## 6. 小众游戏的兜底阈值定不下来，只能靠访谈校准

**现象**：第一版只做精确匹配，玩家一说冷门游戏就冷场——要么瞎猜，要么反问到底。

**原因**：游戏数量数以万计，穷举不可能；而"小众游戏"本身没有清晰边界。

**解法**：改成三级兜底（精确 → 类型/风格 → 反问），并**用小样本玩家访谈校准第二级的 8 条信号规则**。

关键在"从哪找关键词"：**不要从游戏分类学里推导**（会得到"Roguelike""Metroidvania"这种玩家自己都不用的词），而要**从玩家实际怎么描述自己的游戏里提炼**——真实玩家说的是"像素风""剧情很好""喜欢种田""喜欢建造"。第二级兜底的 8 条规则全部来自这个口径。

**教训**：面向用户的分类体系，要用用户的语言，不是行业的语言。

## 7. 智能体会"自作主张"补数据

**现象**：工具返回为空时，模型会顺手编一个价格或场次填进去，读起来非常自然，不仔细核验发现不了。

**原因**：早期提示词只写了"要真实"，**没有写"查不到时怎么办"**。模型遇到空结果，默认行为是"把话说圆"。

**解法**：在提示词里显式规定两条硬约束：
1. **查不到必须走三套兜底预案（同城替代 / 周边城市 / 改期改行程），禁止补数据**
2. **所有推荐必须带名称 + 价格或场次 + 跳转链接，缺任一项即视为不合格输出**

**效果**：加上这两条之后，"无赛事"场景的表现从"编一个"变成了"如实说 + 给替代路径"。第 2 幕和第 5 幕的真实兜底就是这么来的。

**教训**：提示词里"要做什么"只写一半，另一半必须写"做不到时怎么办"。**没有 fallback 规范的提示词等于没有约束。**

## 8. 系统提示词 v1 → v6 的迭代记录

| 版本 | 加了什么 | 暴露出的新问题 |
|---|---|---|
| v1 | 人设 + 工具清单 | 输出像通用攻略，完全没有游戏味 |
| v2 | 「游戏口味地图」知识库 | 有映射了，但只会"游戏名 → 目的地"一对一，千人一面 |
| v3 | 体验意图五分类（竞技/探索/音乐/经营/收集） | 开始出现组合方案，但流程不稳定 |
| v4 | 五步组队法（固定对话流程） | 流程稳定了，但遇到无供给就翻车 |
| v5 | 三套失败兜底预案 | 不翻车了，但偶尔编数据（见第 7 条） |
| v6 | "禁止补数据 + 输出必须含链接"硬约束 | 当前版本 |

**最重要的教训**：提示词工程的迭代动力**几乎全部来自真实对话里暴露的失败**，不来自设计。

v2 的"千人一面"、v4 的"无供给翻车"、v5 的"编数据"，没有一个是靠想出来的，都是跑完对话看输出才发现的。所以**迭代速度比初始设计质量重要得多**——这也是为什么我们选择了"百炼控制台会话"这种改完立刻能验证的形态。

## 附：演示前检查清单

基于以上踩坑整理，每次演示前逐条过：

- [ ] 新建会话，确认返回结果里**没有"体验模式"字样**（Key 已生效）
- [ ] 实查**当前周末**的目标城市赛事 / 演出供给（不依赖彩排缓存）
- [ ] 若当前无供给，**主动把兜底环节编进演示脚本**（这是加分项，不是事故）
- [ ] 确认智能体版本是最新的 v6，没有版本冲突残留
- [ ] 去程 / 回程**分方向各查一次**，不假设对称
- [ ] 检查所有输出项是否都带**价格/场次 + 跳转链接**
