## 二、知识检索的三级匹配

```
玩家输入
   │
   ├─ 提到具体游戏名？
   │     ├─ 命中「主流游戏精确映射」表（30 款游戏 / 20 行映射，5 大类目）
   │     │     └─▶ 直接给出精确映射的目的地 / 场馆 / 活动
   │     │
   │     └─ 未命中
   │           ▼
   ├─ 能否识别类型 / 风格信号？（第二级兜底，8 条规则）
   │     ├─ 能（如"像素风""剧情好""喜欢建造""喜欢种田"
   │     │        "恐怖解谜""音乐节奏""赛车""体育类"）
   │     │     └─▶ 按类型给出方向性推荐
   │     │
   │     └─ 不能
   │           ▼
   └─ 第三级兜底：反问引导
         └─▶ "老板这游戏大概是什么感觉？打怪升级、种田建造，
              还是剧情为主？" —— 不冷场，把玩家拉回可识别区间
```

**扩展规则（写入知识库，约束后续迭代）**

1. 新游戏加入时，**先判定类型标签**（开放世界 / 竞技 / 二次元 / 模拟 / 休闲 / 剧情）
2. 映射的目的地**必须真实存在，且能通过 `search-poi` 或 `keyword-search` 查到真实数据**
3. 演示**优先使用已实测命中的城市与活动**（如成都的演出赛事）

> 第 2 条是本项目主动设的硬约束：**知识库不允许映射到飞猪查不到的地方**。这保证了产出的每一条推荐都是"可预订的"，而不是"灵感建议"。代价是映射范围被飞猪供给覆盖度限制。

## 三、职责边界（谁负责什么）

| 环节 | 由谁负责 | 说明 |
|---|---|---|
| 意图识别 | 模型 | 从自然语言里抽取游戏名 / 类型 / 偏好风格 / 出行三要素 |
| 知识检索 | 模型 + 知识库 | 模型执行匹配动作，映射关系由知识库提供，模型不得自行发明映射 |
| 需求补全 | 模型 | 缺失信息必须追问，不猜 |
| 工具编排 | 模型 | 决定调用哪些 `flyai` 命令、以什么参数、按什么顺序 |
| **数据真伪** | **工具（飞猪）** | **价格 / 场次 / 车次 / 链接一律以工具返回为准，模型不得估算或补写** |
| 推荐逻辑解释 | 模型 | 解释"为什么推荐 A 而非 B"，这是模型的价值所在 |
| 失败兜底 | 模型 + 提示词约束 | 工具返回为空时，必须走三套预案，**禁止编造** |
| 下单支付 | 用户 | 智能体只提供跳转链接，不代下单、不代支付 |

**一句话**：模型负责"理解、编排、解释"，飞猪负责"事实"，用户负责"决策与支付"。三者不越界。

## 四、为什么是「智能体配置」而不是「代码工程」

本项目的交付形态是**系统提示词 + 知识库 + 提示词工程**，运行在百炼 Managed Agent 上，没有独立部署的服务端。

这是有意的取舍：

**好处**
- 直接跑在百炼平台上，是最贴近大赛"用百炼构建 AI 旅行应用"命题的形态
- 知识库可随时扩展，不需要改代码、不需要重新部署
- 迭代成本极低——提示词从 v1 到 v6 全部是在控制台里改完立刻验证

**代价（已在 README 第七节明确说明）**
- 没有可公开点击的 Demo 入口，评委需要自己的百炼账号 + `FLYAI_API_KEY` 才能复现
- 没有自动化测试，正确性靠人工对话验证 + 逐条核对工具返回
- 复杂状态管理（如多轮行程状态回滚）能力受限，这类能力更适合用代码实现
