1为什么做这个

游戏是最诚实的兴趣标签——它是行为，不是自述。

一个在《黑神话：悟空》里泡了 300 小时的玩家，和一个在《星露谷物语》里泡了 300 小时的玩家， 想从旅行里获得的东西完全不同——前者要古建朝圣的震撼，后者要田园治愈的松弛。

但现有旅行 AI 给两个人的答案，大概率是同一份「XX 市必去十大景点」。 一个人在游戏里愿意花时间做什么，直接暴露了他真实的体验偏好； 这个信号比「你平时喜欢什么类型的目的地」可靠得多，因为它是行为，不是自述。

2通用攻略问答给不出什么

同一个问题，两种处理方式。这是实测结果，不是设想。

玩家说：「我玩一个很冷门的像素风独立游戏，周末想去成都玩，但不知道玩啥」

通用攻略问答

  • 按「成都」直接给通用景点列表
  • 宽窄巷子、锦里、大熊猫基地，三件套
  • 不解释为什么是这几个
  • 没有价格、没有车次、没有预订入口
  • 没有赛事就当作没这回事
  • 输出一段文本，看完还得自己去查

游侠出行

  • 先识别小众游戏信号 → 走三级兜底
  • 追问具体游戏名做二次校准，不硬猜
  • 调 search-train 给出真实车次：D49 ¥85 / Z333 ¥50.5 / T8804 ¥50.5
  • 调 search-hotel 给出真实房价：雷泽电竞酒店 ¥29/晚、758 电竞酒店 ¥55/晚
  • 给出推荐逻辑：A 方案 vs B 方案各适合什么状态，1200 预算怎么拆
  • 主动查赛事 → 确认无票 → 如实告知 + 给替代路径
  • 输出三日任务清单，全部带飞猪跳转链接
最后一行是关键：我们主动展示失败。 演示里飞猪本周末确实没有成都体育赛事，智能体没有编一个出来，而是说「暂时没搜到，给你三条替代路径」。 这条兜底在真实会话中触发过 2 次（第 2 幕、第 5 幕）。

三级匹配机制

第二级的关键词来自玩家实际怎么描述自己的游戏——「像素风」「剧情很好」「喜欢种田」「喜欢建造」， 而不是从游戏分类学里推导的「Roguelike」「Metroidvania」。 面向用户的分类体系，要用用户的语言，不是行业的语言。

右侧那条硬约束是本项目主动设的：知识库不允许映射到飞猪查不到的地方。 这保证产出的每一条推荐都是「可预订的」，而不是「灵感建议」。

4五步组队法

把「体验意图理解」做成可复现的流程，而不是靠模型随机发挥。

第 0 步
开场 · 主动服务彩蛋
已知游戏偏好 → 主动推荐对应主题；未知 → 先问一句「老板最近肝什么游戏？」并给出热门选项。
第 1 步
识别玩家画像
从对话里提取游戏名 / 类型 / 偏好风格，查「游戏口味地图」做三级匹配。
第 2 步
挖掘出行需求 + 体验偏好问答
必须确认三要素：目的地 / 时间 / 预算。再用五类偏好问答定位真实需求。
你玩游戏时，最看重下面哪种感觉？
A. 竞技与社交  ·  B. 探索与世界观  ·  C. 音乐与节奏  ·  D. 经营与慢生活  ·  E. 收集与打卡
第 3 步
查真实数据并组装方案
按「玩什么 → 怎么去 → 住哪里 → 顺路玩什么」的完整链路调用工具，每次返回后展示名称、价格、场次、图片与跳转链接。

三套失败兜底预案
① 同城替代体验（目标活动没了，同城换一个同类型的）  ② 周边城市（同城没有，扩到周边）  ③ 改期改行程（都没有，给改期建议或重排）
提示词里显式规定：查不到必须走三套兜底，禁止补数据；所有推荐必须带「名称 + 价格或场次 + 跳转链接」，缺任一项即视为不合格输出。
第 4 步
收尾
提示所有推荐均可在飞猪直接下单（带链接），询问是否调整预算 / 时间 / 城市，重跑方案。

7架构与职责边界

模型负责理解、编排、解释；飞猪负责事实；用户负责决策与支付。三者不越界。

环节由谁负责说明
意图识别模型抽取游戏名 / 类型 / 偏好风格 / 出行三要素
知识检索模型 + 知识库模型执行匹配动作，映射关系由知识库提供，不得自行发明映射
需求补全模型缺失信息必须追问，不猜
工具编排模型决定调用哪些 flyai 命令、什么参数、什么顺序
数据真伪工具（飞猪）价格 / 场次 / 车次 / 链接一律以工具返回为准，模型不得估算或补写
推荐逻辑解释模型解释「为什么推荐 A 而非 B」，这是模型的价值所在
失败兜底模型 + 提示词约束工具返回为空时必须走三套预案，禁止编造
下单支付用户智能体只提供跳转链接，不代下单、不代支付

8边界与已知不足

主动说明边界，比假装全能更可靠。

知识库不是全量游戏库

目前精确映射 30 款游戏（20 行映射）+ 8 类风格兜底。市面游戏数以万计，未收录的游戏会走第二 / 三级兜底，兜底结果的相关性必然低于精确映射。

映射范围被飞猪供给覆盖度限制

扩展规则要求「映射目的地必须能被 flyai 查到真实数据」，这保证了可预订性，但也意味着飞猪供给薄弱的城市，即使旅行体验很契合，也不会被映射进去。

价格与场次随查询日期浮动

页面展示的均为查询当时的快照，最终以飞猪预订页为准。演示中的「本周末无成都体育赛事」是 2026-10-15 的真实返回，换个周末可能就有赛事。

不做预订、不做支付

只提供飞猪跳转链接，下单支付由用户在飞猪 App 完成。不做实时余票锁定，「有票」仅代表查询时刻的状态。

交付形态为智能体配置，不是独立代码仓库

复现方式是在百炼控制台创建智能体并注入 FLYAI_API_KEY。本页与仓库截图 / 验证报告是永久留存证据；百炼会话受状态机管理，归档后为 terminated 终态、不能再交互。

目前没有自动化测试

真实数据链路的正确性靠人工对话验证 + 逐条核对工具返回来保证，而非单元测试。这是明确认知的短板。
